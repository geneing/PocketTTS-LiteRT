# FlowLM on Pixel 10: speed and energy research

Research date: 2026-10-05. Target: Pixel 10 (`frankel`), Tensor G5, PowerVR DXT-48-1536. This is an implementation brief for the existing PocketTTS LiteRT export and Android library. All projected wins below are hypotheses until the paired phone benchmark passes.

## Recommendation

Keep **dynamic range int8 FlowLM on CPU** as the production baseline. The highest-priority accelerator experiment is a **device-resident KV cache**, proved first with a tiny G5 AOT graph. That attacks the 25 MB host-to-accelerator transfer on every step. In parallel, repair prompt prefill for the int8 graph. Once cache residency works, optimize weight storage and bandwidth separately and compare energy per second of speech at a required speed. Do not switch the production LM to the current fp16 GPU or NPU graph on latency alone.

The immediate optimization target is the *whole TTS pipeline*, including text prefill, autoregressive audio frames, Mimi decoding, initialization, and sustained power. For this model, LLM advice about token throughput can mislead: the decoder emits 12.5 latent frames/s of audio, and the host needs each latent and EOS decision before the next frame. Batch prefill is useful; ordinary parallel decode is impossible without changing the model.

## What the repository and phone already establish

`FlowLMStep` is a six-layer, width-1024, 16-head transformer with head dimension 64. The current fused step takes `emb`, RoPE, an additive mask, packed `pk/pv[1,96,512,64]`, and noise, then returns EOS, a 32-element latent, and only the new K/V row. Android stores K/V in float arrays and calls `writeFloat(pk)` and `writeFloat(pv)` for **every** token or frame. Those two inputs total **25,165,824 bytes per invocation**; the useful output is about 49 KB. `PMAX=512` is a joint capacity for voice, text, and audio frames. The host computes the next audio embedding from the previous latent. See [`FlowLMStep`](../scripts/build_pockettts.py), [`PocketTtsSession.step`](../pockettts-core/src/main/kotlin/dev/pockettts/PocketTtsSession.kt), and [`PocketTts`](../pockettts-core/src/main/kotlin/dev/pockettts/PocketTts.kt).

Current Pixel 10 measurements, with different protocols kept separate:

| Path | Measured result | Interpretation |
|---|---:|---|
| CPU dynamic int8, 128-step microbench | 1.50 ms input + 8.65 ms run + 0.12 ms read per frame | Fastest shipped LM; 81.7 MB graph; 2.16x end-to-end RTF in the 95-character benchmark. |
| CPU fp16, same microbench | 1.33 + 19.59 + 0.13 ms | Weight bandwidth matters more than arithmetic for batch-one decode. |
| NPU fp16, one-step microbench | 6.30 + 15.77 + 0.51 ms in one record | NPU compute is faster than fp16 CPU, yet staging erases that advantage. It has not beaten CPU int8. |
| NPU fp16, four/eight-step unroll | 26.90/26.81 ms *per frame* for run, plus input/read | Fewer transfers did not compensate for unrolled graph work on the tested NPU export. |
| GPU fp16 or dynamic int8, 201-word paired power test | 97.0/93.4 s to synthesize about 60 s speech | Fully delegated, yet readback/synchronization and 25 MB uploads dominate. |
| CPU int8 vs GPU int8, paired energy test | 26.9 J vs 22.7 J incremental estimate | GPU used less estimated energy but was roughly 3.8x slower, so it misses the joint speed/energy goal. |
| CPU fp16 vs NPU fp16, paired energy test | 52.9 J vs 16.6 J incremental estimate | NPU has a potentially useful energy advantage, but its 48.7 s runtime was slower than CPU fp16's 36.4 s; compare it against **CPU int8** before any policy change. |

Records: [`docs/int8_lm.md`](int8_lm.md), [`docs/flowlm-optimization-results.md`](flowlm-optimization-results.md), and [`docs/bench/2026-09-19-pixel10-optim-tensor_g5-npu-multistep.txt`](bench/2026-09-19-pixel10-optim-tensor_g5-npu-multistep.txt). These are measurements of specific graphs, not a general CPU/GPU/NPU ranking. The previous strict waveform-correlation gate in [`docs/multistep_lm_plan.md`](multistep_lm_plan.md) is superseded for free-running speech: the user listened to the low-correlation GPU and NPU samples and found them acceptable. Use text intelligibility, completion, duration, stability, and listening as quality gates; report waveform correlation as a diagnostic.

The fused graph already has a fixed-16 headless `prefill` signature, but `usePrefill=false`: it has not reproduced sequential per-token results on the int8 graph, and padding can waste work. The exporter previously checked the wrong signature index; its current index-0 check exposes the issue. Fix this before using any batched prefill result as a performance claim. See [`PrefillStep`](../scripts/build_pockettts.py), [`PocketTtsConfig`](../pockettts-core/src/main/kotlin/dev/pockettts/PocketTtsConfig.kt), and [`LatencyProbeTest`](../app/src/androidTest/java/com/pockettts/LatencyProbeTest.kt).

### Memory traffic: measure three different costs

| Cost | Current behavior | Optimization target |
|---|---|---|
| **Host-to-accelerator K/V per invocation** | `writeFloat(pk)` and `writeFloat(pv)` send 25.2 MB of fp32 cache even though only one K/V row changes. NPU staging is about 6 ms/step in one device record; GPU upload and completion are much worse. | Keep cache in compatible GPU/NPU buffers across steps, then send only the 1024-element input, 32-element noise, small position/mask data, and read 33 output floats. Prove whether buffer chaining actually avoids internal copies. |
| **Model-weight placement at load** | The 81.7 MB int8 or 161.4 MB fp16 graph is loaded/compiled once per engine, not passed as a Kotlin input on every frame. GPU's documented quantized path dequantizes constant weights into GPU memory when the delegate is enabled. | Measure cold load, peak residency, and any first-run upload/compilation. Reuse one engine; do not count graph-file size as a per-step host copy. |
| **Weight reads during each decode step** | Batch-one matrix-vector work can stream weights from device DRAM on every frame even when they are already device-resident. The repository's CPU int8 versus fp16 timing strongly suggests bandwidth pressure, but does not directly measure NPU/GPU DRAM bytes. | Try native accelerator-compatible int8/mixed-precision weights and weight reuse/fusion; profile sustained time and energy. Do not assume that AOT compilation or zero-copy KV makes weights fit in TPU/GPU on-chip memory. |

This distinction matters because a cache-buffer redesign can remove **host/device** traffic while quantization and architecture changes attack **weight memory bandwidth**. Neither benefit is implied by the other. The [LiteRT GPU quantization guide](https://developers.google.com/edge/litert/performance/gpu) documents one-time constant dequantization for GPU; it does not promise quantized GPU arithmetic. For NPU, establish the actual compiled tensor dtypes and buffer placement from the AOT report and device trace.

## Lessons from other Android LLM implementations

1. **Separate prefill from decode.** Google's [LiteRT-LM Tensor G5 guide](https://developers.google.com/edge/litert/next/litert_lm_npu) publishes an AOT Gemma 3 1B model with 8-bit per-channel weights and a 1280-token context, and runs it through `litert_lm_main --backend=npu`. That demonstrates that G5 can execute an LLM with a KV cache. It does **not** mean the stock LiteRT-LM executor can run Pocket TTS: this model consumes embeddings and emits a latent plus EOS, followed by a flow head and host projection rather than token IDs and vocabulary logits. The [Tensor SDK v1.02 notes](https://developers.google.com/edge/tensor-sdk/release-notes) also describe a Pixel TPU LiteRT-LM chatbot demo. Use its AOT/runtime/dispatch wiring as a reference, not its token sampler as an adapter.
2. **Treat shape variability differently by backend.** The [Tensor SDK FAQ](https://developers.google.com/edge/tensor-sdk/tensor-faqs) says the G5 AOT compiler requires static shapes. For NPU, compile a small set of fixed prefill buckets (for example 1, 8, 16, 32) and run a chunk loop; pad the last chunk with rows that cannot write cache. Do not compile one model per possible prompt length or attempt `resize_tensor_input` on an AOT artifact. On GPU, the [LiteRT Torch release notes](https://github.com/google-ai-edge/litert-torch/releases/tag/v0.9.4) include dynamic prefill/cache export flags, but that is a separate generative exporter path. First prove this custom graph and the Pixel PowerVR delegate support the specific dynamic dimension and avoid recompilation or CPU partitions. Fixed buckets remain the lower-risk choice.
3. **Keep tensors on the accelerator only when the whole loop benefits.** LiteRT documents [GPU zero-copy buffers and asynchronous execution](https://developers.google.com/edge/litert/next/gpu) and [NPU AHardwareBuffer zero-copy and chaining](https://developers.google.com/edge/litert/next/npu). These APIs make a resident-cache experiment plausible; they do not guarantee in-place K/V mutation or that an AOT graph's output can alias its next input. Verify buffer types and actual transfer cost before designing around them. The legacy [GPU delegate performance guide](https://developers.google.com/edge/litert/performance/gpu) warns that partial CPU/GPU partitioning adds synchronization and that reshapes can be expensive. On Pixel 10, a fully delegated graph is already slow, so zero-copy and fewer dispatches need real measurement.
4. **AOT and runtime versions must match.** Tensor G5 uses AOT via `CompiledModel`, not JIT in the current [NPU guide](https://developers.google.com/edge/litert/next/npu). The [Tensor SDK compatibility table](https://developers.google.com/edge/tensor-sdk/release-notes) and [FAQ](https://developers.google.com/edge/tensor-sdk/tensor-faqs) call out the appropriate LiteRT/dispatch pair; the FAQ recommends a 2.1.6 dispatch for G5. Pin compiler, Android runtime, and dispatch together in the experiment. Record compilation report, partition count, firmware/build fingerprint, and actual accelerator at runtime. A successful AOT compilation alone is not a speed or correctness result.
5. **Measure in a foreground app.** Google's [CompiledModel benchmark guide](https://developers.google.com/edge/litert/next/benchmark) warns that `adb shell` binaries can receive different scheduler treatment from an Android app. The repository's `PowerBenchmarkTest` uses Android power monitors and paired audio-only subtraction; retain that structure. The [Android power-monitor API](https://developer.android.com/reference/android/os/PowerMonitorReadings) reports energy since boot in microwatt-seconds, so the values are estimates affected by the rest of the device.

## Ranked implementation options

Ranking is by importance to the joint speed/energy goal on this Pixel 10, then expected deployability. A lower-ranked option can win after evidence changes. Each option is an independent agent handoff with a stop condition.

### 1. Prove a persistent NPU cache and then re-author a stateful G5 FlowLM

**Value:** highest plausible energy benefit, potentially faster than fp16 NPU; high implementation risk. The measured NPU has low estimated energy but loses time to cache staging and possibly precision changes. This option must beat CPU int8 on the chosen speed/energy objective to ship.

**First gate, before a full export:** Build a tiny fixed-shape AOT test model taking a cache tensor and a one-row update, returning a new cache plus one scalar. Allocate two NPU-compatible cache buffers and alternate them without `readFloat`/`writeFloat` between invocations. Measure copy, run, sync, and memory. Test whether an output buffer can be bound directly as the next input and whether any alias/in-place route is supported; use a two-bank scheme if aliasing is unsafe. Inspect the actual buffer type and dispatch logs. The proof should report host bytes per step and whether the NPU still performs a full 25 MB *device-side* cache copy. If the runtime copies 25 MB through host memory or cannot retain/cache-chain the tensor, stop this branch and do not port the full model.

**Full design if gate passes:** Export a fixed one-step graph with the existing fused flow head. Inputs are one embedding, noise, position or RoPE, and two resident caches; outputs are EOS, latent, and the next resident caches (or sparse K/V updates if the runtime exposes a supported cache-update op). Keep the CPU-visible result to 33 floats. Put position/mask construction inside the graph only if the G5 AOT compiler accepts it; otherwise send a small fixed-shape position/mask. Keep K/V in fp16 or fp32 only after measured quality and energy comparison. Use separate static prefill bucket signatures from option 2. Use the same model instance across an utterance and reset/cache-load voice state once per utterance. Pin the AOT compiler/dispatch/runtime according to the SDK matrix. A partial NPU partition may erase gains; record actual offload and reject a result with hidden CPU fallback.

**Further optimization after correctness:** Try NPU-compatible per-channel int8 weights, mixed precision for the small EOS projection and flow head, and the Tensor SDK performance modes (`Balanced`, `SustainedPerformance`, `PowerSaver`) if exposed by the pinned runtime; measure each mode rather than assuming the fastest mode is most efficient. Distinguish one-time weight upload at load from repeated DRAM reads: compare warm decode and energy after changing only weight dtype, then compare cold load and RSS. The SDK [release notes](https://developers.google.com/edge/tensor-sdk/release-notes) say those controls exist, and the [Google Tensor options API](https://chromium.googlesource.com/external/github.com/google-ai-edge/LiteRT/+/d846569552c71f0c0b05f89476f865f3979e0a12/litert/c/options/litert_google_tensor_options.cc) exposes a performance-mode setter.

**Verify/stop:** Compare against **CPU int8** on short/long text, one-shot and streaming, warm/cold start, and sustained repeated runs. Require no early truncation and acceptable listened speech. Report p50/p95 first audio, total synthesis time, joules per second of generated audio, joules per utterance, load/RSS, temperature and speed drift. If it remains slower than the CPU baseline with no product-acceptable energy advantage, retain it only as an opt-in low-power path.

### 2. Repair and bucket prompt prefill on the CPU int8 path

**Value:** high speed gain for prompts, low deployment risk, medium implementation effort. It preserves the measured fast decode path. The benefit grows with prompt length; it does not accelerate generated frames.

**Implement:** In `scripts/build_pockettts.py`, establish a token-by-token oracle from `FlowLMStep` using a real preset voice, then compare each real K/V row from `PrefillStep` at every layer/head and position in eager fp32, TFLite fp32, and the shipped int8 graph. Fix the first divergent row and confirm the signature index and I/O order. Use a headless prefill graph; do not run the flow head or sample noise for text. Generate fixed `P={1,8,16,32}` signatures or a small number of separate artifacts after measuring memory cost. In `PocketTtsSession.prefill`, choose the largest bucket no bigger than remaining real tokens, or use a padded bucket only if padding is proved inert and cheaper than several smaller calls. Preserve the voice prefix, absolute RoPE offsets, and exact causal mask. Write only real K/V rows back; never advance `pos` for padding. Keep step decode in the existing `dyn8_all` graph. Share backbone weights if a multi-signature file does not create a prohibitive runtime memory cost.

**Verify/stop:** Cover prompt sizes 1, 7, 8, 9, 15, 16, 17, 31, 32, 33, 50; at least two voices and a prompt near `PMAX`. Compare every real new K/V row and the first subsequent decode step with sequential int8, then listen to full speech and verify no early EOS or missing words. Report prefill ms/token, first-audio latency, peak RSS, model load time, and total joules. Keep `usePrefill` off unless the *quantized device* path wins and passes these checks. Do not infer correctness from one whole-output correlation.

### 3. Reduce active KV work with context buckets, then test KV precision

**Value:** moderate potential speed and energy, medium/high quality risk. It is useful on CPU and could make NPU state residency easier. Current cache I/O is 25.2 MB regardless of the actual position, and attention scores include 513 columns even early in an utterance.

**Implement:** Export static decode capacities such as 128, 256, and 512 positions, selecting the smallest capacity that safely contains the voice prefix, prompt, and *planned* maximum generated frames. Keep the fallback 512 graph. The app should not guess that an utterance will end early; use its existing frame-budget calculation plus a margin, or switch to a larger graph only by reconstructing the complete cache and proving state transfer. For CPU, benchmark whether reduced attention and smaller `writeFloat` buffers overcome extra model residency/load cost. For NPU, compile each static bucket only after option 1's cache gate. Next, test fp16 K/V I/O or per-head int8 K/V with explicit scales and a separate EOS/latent quality assessment. Do not equate 8-bit *weight* quantization with 8-bit KV quantization; the current `dyn8_all` leaves KV fp32. Keep voice caches convertible without rebuilding APKs.

**Verify/stop:** Test the longest supported voice/prompt/audio combinations, exact `PMAX` boundary, and long streaming chunks. Compare first divergent step, speech completion, and energy. A capacity miss must fall back or fail clearly before synthesis, never silently discard older positions. If a sliding window is attempted, preserve the voice prefix, use absolute RoPE positions, and treat it as a model-behavior change requiring listening and transcription across long text.

### 4. GPU resident-cache prototype, only if it eliminates the Pixel 10 round trip

**Value:** uncertain on PowerVR; potentially portable to Mali/Adreno. The current GPU graphs are much slower, and dynamic-int8 weights do not fix that because GPU execution uses a floating-point view of quantized weights per Google's [GPU guide](https://developers.google.com/edge/litert/performance/gpu). A direct port of the current fixed graph is already disproven by device data.

**Implement:** Use LiteRT `CompiledModel` C++ buffer APIs to chain a tiny cache-update graph through OpenGL/OpenCL-backed buffers, with only latent/EOS read to CPU. Prototype with fixed shapes first, then a dynamic active-length dimension if a device trace proves it does not recompile or partition. Compare a 1-step graph against N=2/4 unrolls; earlier fp16 GPU N=4 power measurement was interrupted, so that one isolated experiment remains informative. If the large cache cannot persist, stop. Keep graph ops fully delegated and avoid expensive reshape/transpose chains; record rejected ops and kernel/partition counts. A full LiteRT-LM migration is a separate research project because its token-logit executor cannot directly drive this latent-feedback TTS loop.

**Verify/stop:** Require actual end-to-end speed above CPU int8 on Pixel 10, or a clearly justified energy-limited mode. Benchmark cold load, first audio, sustained paragraph, and PowerVR precision mode. Do not accept `run()` timing by itself: GPU work may complete at `readFloat()` and the measured read can dominate.

### 5. Change the model architecture and retrain/distill for mobile decode

**Value:** highest ceiling; highest model, data, and quality cost. Use after system-level bottlenecks are quantified, or if a product target cannot be reached with the existing weights.

**Implement candidates:** (a) Grouped-query or multi-query attention so 16 query heads share fewer K/V heads; at 4 K/V heads the cache drops about 4x, but existing weights cannot simply be reshaped without fidelity loss. (b) Smaller transformer width/FFN or fewer layers, distilled from the current speech distribution. (c) Local-window attention with an immutable voice-prefix memory or compressed voice conditioning, so long utterances do not carry all previous audio frames. (d) Reduce per-frame flow-head cost by distilling a smaller head or moving latent-to-embedding projection into the graph, while keeping one-step generation semantics. Quantization-aware training or selective high-precision EOS may recover quality if more aggressive weights/KV quantization is desired.

**Verify/stop:** Build a held-out suite across voices, text lengths, numerals, punctuation, and long passages. Use intelligibility/transcription, truncation and length, speaker similarity, artifact listening, and repeated-seed stability; waveform correlation is only a diagnostic. Publish parameter count, K/V bytes, AOT partition report, load/RSS, first-audio latency, sustained RTF, and energy. Do not replace the pretrained model on synthetic parity alone.

### 6. Retune CPU int8 as a low-risk fallback improvement

**Value:** lower ceiling but useful for every phone and mandatory as a control. Current `dyn8_all` already performs well; 4-bit and static int8 variants were faster or smaller in isolated areas but failed speech quality/completion, while weight-only int8 did not speed compute. See [`docs/int8_lm.md`](int8_lm.md).

**Implement:** Profile FC versus attention versus copies with the in-app harness. Try a selective fp32 `out_eos` projection while keeping dynamic int8 elsewhere; it is tiny and sensitive to the `-4` EOS threshold. Examine dynamic-int8 granularity and thread count with *paired* end-to-end benchmarks. If variable-capacity graphs from option 3 work, combine the fastest CPU graph with the corrected prefill. Avoid spending a large implementation cycle on int4 before a mixed-precision or trained quantization recipe passes listening.

**Verify/stop:** A candidate must improve median and p95 full-pipeline time or joules without truncation, not merely shrink the model file. Report model size and cold start as well as warm frame time.

## Variable-length input design for an implementing agent

The prompt length varies, but the autoregressive decode input is always one frame. On **G5 NPU**, keep tensor shapes static: choose a prefill signature from a small bucket set, run several chunks for longer prompts, and pass a `valid_count`/write mask so padding never enters cache or position. The last real prompt token must be visible to the first audio/BOS step. A prompt of length zero should take no prefill call. The joint context limit is `voice_len + prompt_len + generated_frames <= capacity`; validate before choosing a graph and before every step. Do not confuse token *batching* with independent requests: rows are causal and must attend to earlier real rows, including those in the same batch.

On **GPU**, dynamic sequence length is worth trying only when it reduces work/transfer without shader recompilation or delegation loss; support in another LiteRT-LM exporter does not prove it for this graph or PowerVR. A fixed bucket can win through stable compilation and program-cache reuse even if some rows are padded. On **CPU**, dynamic shapes may be easier, but the app's fixed `CompiledModel` buffers and joint capacity still favor a small number of buckets until measurements justify a resize path. Keep a single-step decode graph as the universal correctness fallback.

## Benchmark and acceptance protocol

1. Preserve the existing production configuration (`lm:CPU` with `pt_flowlm_fused_dyn8_all.tflite`, `dectx:NPU` when available, `dec:GPU`) as the A/B control. Run a single instrumentation method at a time. `:app:connectedDebugAndroidTest` uninstalls the app and erases pushed models; use `:app:installDebug :app:installDebugAndroidTest` and `adb shell am instrument -w -e class ...` as in the repo instructions.
2. Use 3 prompt regimes (1-5, 25-50, and near capacity tokens) and 3 audio regimes (short, medium, long), at least two voices, same seed, and a fixed device build. Separate prefill, per-frame copy, actual compute/sync, read, Mimi, and load. Include cold start and warmed steady state. For NPU/GPU, log actual backend and AOT partition report; an unrecognized graph or fallback is a failed experiment.
3. Measure in-app wall time and Android power monitors in paired A/B order, with an audio-only interval and similar screen/network/thermal state. Repeat in reversed order. Report total J, J/s of speech, RTF, first-audio p50/p95, peak RSS, and temperature/sustained drift. An energy number without its synthesis duration is not a power/latency decision.
4. Make every graph pass eager-vs-TFLite parity at the tensor/step level. For generated speech, require complete text, stable speaker, no early EOS or artifacts, and listening review. Compare several seeds; autoregressive numerical divergence makes low waveform correlation insufficient to reject speech by itself.
5. Commit text reports in `docs/bench/` with the graph checksum, SDK/runtime/dispatch version, device fingerprint, test text/voice/seed, and the exact power measurement method. Keep WAVs available locally for listening. Do not label an option a win until it beats the CPU int8 control under the same decoder placement and workload.
